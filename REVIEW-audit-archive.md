## Executive summary

**The security and data fundamentals are genuinely strong.** The audit specifically tried to break these and could not: authorization is mature (every sampled API scopes reads/writes to `session.user.id`; teacher routes verify ownership; admin routes use `requireAdmin()` with audit logging; the admin-only `mondo_view_as` "view as" cookie is correctly honored *only* when the real role is ADMIN, so a non-admin can't forge premium/teacher/admin). There is **no SQL injection** (all raw SQL is parameterized), **no SSRF**, open-redirect is handled, rate limiting covers the abuse-prone endpoints, the Stripe webhook is signature-verified and idempotent, every competitive write path uses `$transaction` + `SELECT … FOR UPDATE`, and account-deletion cascades are complete. The core scoring math (Elo MMR, MCAT curve, AP blends) is correct and server-authoritative in competitive play.

**The real issues cluster in four themes**, none of which are "the foundation is broken" — they're wiring, compliance, and polish gaps:

**① Child-safety & privacy compliance — the highest-stakes cluster (legal exposure for a platform serving ~9-year-olds).**
- No age gate or COPPA/parental-consent flow, while the privacy policy claims you "do not knowingly collect" data from under-13s (you serve grade-4 math). *(reviewer-critical → verified high)*
- Microsoft Clarity **session replay** runs with no consent gate, identifies authenticated minors, and is undisclosed in the policy/cookie banner.
- AdSense runs on grade 4–8 pages with no child-directed-treatment signal.
- Full **real names** are exposed to randomly-matched stranger opponents (ranked matches) and via an **unauthenticated** diagnostic-challenge share endpoint (names / email local-parts) — the leaderboard name-masking is bypassed exactly where minors meet strangers.

**② Billing is partly broken and untruthful.**
- The **Annual plan is advertised and selectable but checkout always charges the monthly price** (the billing param is ignored). *(reviewer-critical → verified high)*
- The Stripe webhook reads `current_period_end` from the wrong object for the pinned API version (writes `Invalid Date`) and there's no handler for failed payments / mid-cycle changes; expiry is never enforced.
- Post-checkout `success_url` points to a route that doesn't exist → **paying users land on a 404.**

**③ Assessment results are client-trusted (integrity + score-inflation).**
- Exit-quiz `score`/`passed`/`mustRedoUnit` are computed in the browser and stored verbatim — this gates topic **MASTERED** status and competitive unlock, so it's forgeable.
- The exit-quiz schema even allows `score > totalQuestions`, which inflates every AP/SAT/ACT/MCAT score predictor; SAT full-test scaled scores are likewise client-computed and unbounded.

**④ Learning-flow & content seams have user-visible bugs.**
- New flashcards surfaced by the session endpoint **can never be reviewed or scheduled** (their review POST 404s and is swallowed).
- The "weak topics" recommender compares a 0–100 value against 0–1 mastery, so it flags *every* started topic (even mastered) as weak.
- Dashboard **"Time Studied" is always 0** (every lesson save hardcodes `timeSpent: 0`); the streak count displays stale values.
- **22 student-facing topics** render a one-line placeholder (no lesson, problems, or flashcards); the **primary** flashcard study view renders LaTeX as raw text (`$`, `\frac`) for ~1,123 math cards.
- The sitemap submits ~90 interactive-lesson URLs that 404 (registry keys ≠ DB Topic slugs) — same root cause as the lesson-slug reconciliation done earlier.

Plus a long tail of **performance** (an N+1 doing ~1,000 round-trips; the 716 KB `registry.ts`; client bundles shipping 84 KB / 2.3 MB datasets), **accessibility** (quiz answer-selection is color-only with no `aria-pressed`/`role=radio`; timed exams lack `aria-live`), **SEO** (duplicate-content route pairs; a broken structured-data logo; ~200 pages inheriting the homepage OG title), and **code-health** items (a public `/test/remediation` dev page indexable in prod; built-in Toast/ErrorBoundary/EmptyState systems are dead code; an orphaned "Study Groups" feature).

**Suggested order of attack:** ① child-safety/compliance (legal) → ② billing (revenue + trust) → ③ server-side exit-quiz scoring (integrity) → ④ the flashcard-review 404, weak-topics threshold, and 22 placeholder topics (visible breakage) → then the perf/a11y/SEO/code-health tail. Full detail, evidence, and fixes per item below.

### 1. Quiz/exam answer selection is conveyed by color only — no aria-pressed/role=radio (screen-reader users can't tell which option they chose)
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Accessibility (ARIA / form semantics in the core learning loop)

- **Files:** `src/components/TopicEntranceQuiz.tsx:275-284`, `src/components/ExitQuiz.tsx:404-445`, `src/components/PracticeExam.tsx:330-338`
- **Impact:** Blind/low-vision students using a screen reader get no programmatic feedback about which answer they have selected before confirming, on the platform's central activity (exit quizzes gate competitive mode, practice exams are timed). This affects every quiz and exam across all courses. The audience explicitly includes many minors who may rely on AT.
- **Evidence:** Every quiz renders options as plain <button> elements whose selected state is purely visual. In ExitQuiz.tsx:418-419 the only difference for a chosen option is `style = 'border-purple-500 bg-purple-50 ... ring-2 ring-purple-300'`; the button has no aria-pressed/aria-checked and the group has no role=radiogroup. Same in TopicEntranceQuiz.tsx:275-284 (`onClick={() => setSelectedAnswer(idx)}`, state shown via `borderColor`/`bgColor` only) and PracticeExam.tsx:331-336 (`const isSel = answers[idx] === i` toggles `t.sel` classes only). A screen reader announces 'A. <text>, button' identically whether or not it is the currently selected answer.
- **Verifier note:** Claim is accurate. Minor clarifications: (1) The options are native <button> elements (not divs), so they are keyboard-focusable and announced as "button" — the controls are operable, the defect is purely that selected STATE is not exposed (missing aria-pressed/aria-checked/role=radio + radiogroup). (2) ExitQuiz additionally renders a filled letter badge for the selected option (bg-purple-500 text-white, line 435), but this is still a color/visual-only cue with no text or ARIA, so it does not mitigate the issue. (3) The reviewer's ExitQuiz line cite is right: the chosen-option style at line 419 is the ring-2 ring-purple-300 string. Severity remains high for AT users; note overall reachability is gated by the small fraction of users relying on screen readers, but within that population the impact on the core learning loop is significant and spans every course.
- **Fix:** Model option lists as a radio group: wrap in role="radiogroup" with aria-label, and either use real <input type=radio> with associated <label>, or add role="radio" + aria-checked={isSelected} to each option button (and aria-disabled when eliminated/locked). At minimum add aria-pressed={isSelected} to the existing buttons so selection is exposed to AT.

### 3. New flashcards from the session endpoint can never be reviewed or scheduled — their progress never advances
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Learning Flow & Progress (SM-2 spaced repetition / flashcard progress)

- **Files:** `src/app/api/flashcards/session/route.ts:44-56`, `src/app/api/flashcards/review/route.ts:34-48`, `src/components/FlashcardStudySession.tsx:62-92`, `src/app/dashboard/page.tsx:887`
- **Impact:** Any never-seen flashcard reviewed from the dashboard study session has its rating silently dropped and no SM-2 schedule created. The card stays in the 'new' bucket forever and will be re-served as new on every session — progress for newly generated cards never advances. The spaced-repetition loop is broken for the common 'study from dashboard' entry point.
- **Evidence:** GET /api/flashcards/session deliberately returns brand-new cards that have NO FlashcardProgress row ('progress: { none: { userId } }', route line 45-56). The client FlashcardStudySession.handleRating POSTs EVERY rating — including for these new cards — to /api/flashcards/review (line 74-78). But POST /api/flashcards/review does 'const progress = await prisma.flashcardProgress.findUnique(...)' and, when none exists, returns 404 'Flashcard progress not found' WITHOUT creating a row (route lines 43-48). It never calls calculateNextReview/createMany for a missing row. The client swallows the error ('catch { console.error(...) }', line 79-81), so the user sees the card flip and advance, but nothing is persisted. This component is rendered on the main dashboard with no topicSlug (dashboard page line 887), so its session mixes new + due cards.
- **Verifier note:** Accurate as written, with one scoping nuance the reviewer already implied: only flashcards lacking a per-user FlashcardProgress row are affected. Cards already initialized through lesson completion (progress/save), exit-quiz/submit, flashcards/auto-generate, or add-from-missed DO have rows, so the session's "due" branch works for them. The breakage is limited to genuinely-new/uninitialized cards (which are plentiful because bulk seed scripts create Flashcard rows without progress rows). For those cards, ratings from the dashboard study session are silently dropped (404, swallowed by the client's missing response.ok check) and they are re-served as "new" indefinitely. A correct fix is to upsert/create the FlashcardProgress row in POST /api/flashcards/review when none exists, then run SM-2, rather than returning 404.
- **Fix:** In POST /api/flashcards/review, when no FlashcardProgress exists, treat it as a first review: upsert a row (defaults easeFactor 2.5, interval 0, repetitions 0) and run calculateNextReview, instead of returning 404. Alternatively, have the session endpoint create progress rows for new cards before returning them, or have the client surface/retry failures rather than swallowing them.

### 4. Exit-quiz pass/fail and mastery are decided by the client; server stores score, passed and mustRedoUnit verbatim with no recomputation
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Quiz/Diagnostic/Exam Correctness (Exit quiz scoring + pass/unlock thresholds)

- **Files:** `src/app/api/exit-quiz/submit/route.ts:12-31`, `src/app/api/exit-quiz/submit/route.ts:51-139`, `src/components/ExitQuiz.tsx:149-201`, `src/app/api/exit-quiz/status/route.ts:33`
- **Impact:** A user can POST `{score: 0, totalQuestions: 10, passed: true}` (or `score: 10`) to /api/exit-quiz/submit and instantly mark any topic MASTERED and unlock competitive mode, bypassing the 70% gate. This corrupts mastery data that feeds dashboards, study plans, teacher classroom views, and the score predictors, and defeats the intended learning gate for every course's exit quizzes.
- **Evidence:** The submit route accepts `score`, `passed`, `mustRedoUnit` from the request body (`const { topicSlug, score, totalQuestions, passed, mustRedoUnit, answers ... } = parsed.data`) and writes them straight to the DB (`passed: !!passed`, `mustRedoUnit: !!mustRedoUnit`, `score`). It never re-derives pass/fail from score, and never checks that `score` matches the `answers` array. The pass threshold lives only on the client: ExitQuiz.tsx computes `const passThreshold = Math.ceil(totalQuestions * EXIT_QUIZ_PASS_FRACTION)` and `const passed = score >= passThreshold`, then POSTs that boolean. When `passed` is true the server sets TopicProgress `status: 'MASTERED'`, `masteryLevel: 1.0` and upserts `competitiveProfile.competitiveModeUnlocked: true`. The status route trusts it back unchanged: `const hasPassed = attempts.some(a => a.passed)`. The async-challenge endpoint shows the correct pattern the codebase already knows — it scores server-side against stored questions (async-challenge/[id]/route.ts:156-164 `const correct = a.answerIndex === correctIdx; if (correct) score++`).
- **Verifier note:** Claim is accurate. Two refinements: (1) Severity is high, not critical — this is a self-grade/integrity bypass of the actor's own progress and competitive-mode unlock; it does not expose or destroy other users' data, though it does pollute aggregate teacher/dashboard/predictor data. (2) The fix is not a trivial "re-derive passed from score" — because exit-quiz questions are generated client-side (generateExitQuiz) and their correct indices are never persisted with the attempt, the server currently has no stored answer key to re-score the submitted answers against. A real fix needs to (a) at minimum recompute passed/mustRedoUnit server-side from a trusted score, and ideally (b) persist/derive the canonical question set server-side and score the answers array there (as competitive/async-challenge/[id]/route.ts already does), rather than trusting the client's score or per-answer `correct` flags.
- **Fix:** Treat client-sent score/passed/mustRedoUnit as untrusted. At minimum, enforce internal consistency server-side: reject or recompute when `score > totalQuestions`, when `score !== answers.filter(a => a.correct).length`, and recompute `passed = score >= Math.ceil(totalQuestions * EXIT_QUIZ_PASS_FRACTION)` / `mustRedoUnit = score < Math.ceil(totalQuestions * EXIT_QUIZ_REDO_FRACTION)` from the shared constants in src/lib/mastery.ts instead of trusting the booleans. Ideally ship the quiz questions/answers from the server (as competitive does) and score them there.

### 5. Annual plan is advertised and selectable but checkout always charges the monthly price (billing param ignored)
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Payments, Pricing & Ads (Stripe checkout / pricing truthfulness)

- **Files:** `src/app/pricing/PricingPageClient.tsx:27-49`, `src/app/pricing/PricingPageClient.tsx:113-118`, `src/app/pricing/PricingPageClient.tsx:163-168`, `src/app/api/stripe/checkout/route.ts:6`, `src/app/api/stripe/checkout/route.ts:57-66`, `src/lib/premium.ts:77-80`
- **Impact:** Direct billing misrepresentation: the advertised annual discount cannot actually be purchased. Either the user is charged the monthly price after choosing annual (overcharged vs. the displayed $7.99/$95.88), or, if the single price ID is actually the monthly one, the 'Save 20%' / annual offer is entirely fictitious. This is a consumer-protection/false-advertising and chargeback risk on a paid product.
- **Evidence:** The pricing page offers an Annual toggle priced at $7.99/mo with a 'Save 20%' badge and 'Billed annually ($95.88/year)' copy (PREMIUM_PRICING.annual = 7.99, annualPrice*12 = 95.88), and posts the choice to checkout: `body: JSON.stringify({ billing })` (PricingPageClient.tsx:48). But the checkout handler is `export async function POST()` with NO parameter — it never reads the request body. It hardcodes a single line item: `price: process.env.STRIPE_PREMIUM_PRICE_ID, quantity: 1` (checkout/route.ts:62-65). There is no STRIPE_PREMIUM_ANNUAL_PRICE_ID anywhere in the codebase or .env (only STRIPE_PREMIUM_PRICE_ID exists). So a user who picks 'Annual' at the displayed $7.99/mo / $95.88/yr is sent to Stripe Checkout for the single configured (monthly $9.99) price.
- **Verifier note:** The defect is real and the annual offer is genuinely unbuyable, but the precise outcome is slightly different from "always charges the monthly price." Stripe's billing interval (monthly vs annual) is a property of the configured Price object, not of this code; the handler simply charges whatever single STRIPE_PREMIUM_PRICE_ID resolves to. Given PLANS.PREMIUM.price = 9.99 (stripe.ts:36) and PREMIUM_PRICING.monthly = 9.99 (premium.ts:78), the configured Price is almost certainly the monthly $9.99 one — so an annual-selecting user is billed the monthly plan, and the displayed $7.99/mo / $95.88/yr annual discount cannot be honored. Severity adjusted to high rather than critical: it is a true pricing-truthfulness / false-advertising / chargeback risk on a paid product, but it is (a) gated behind Stripe actually being configured (returns 503 with a clear message if STRIPE_PREMIUM_PRICE_ID is unset, route.ts:9-14), (b) requires an authenticated user to complete a real purchase, and (c) is a missing-feature/billing-misrepresentation gap rather than a security, data-exposure, or unbounded-overcharge bug. Fix: read `billing` from the request body and map annual -> a STRIPE_PREMIUM_ANNUAL_PRICE_ID (which must first be created in Stripe and added to env), or remove the Annual toggle until the annual Price exists.
- **Fix:** Have the checkout route read `billing` from the request body and select between STRIPE_PREMIUM_PRICE_ID (monthly) and a new STRIPE_PREMIUM_ANNUAL_PRICE_ID (annual), validating the value server-side. Until an annual price exists in Stripe, remove the Annual toggle and the 'Save 20%'/annual copy from the pricing and /premium pages so the UI cannot promise a plan that isn't sold.

### 6. current_period_end read from the wrong object for the pinned API version (writes Invalid Date) and never used to enforce expiry; no handler for failed payments / subscription updates
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Payments, Pricing & Ads (Stripe webhook / subscription state sync)

- **Files:** `src/app/api/stripe/webhook/route.ts:76`, `src/app/api/stripe/webhook/route.ts:94`, `src/app/api/stripe/webhook/route.ts:60-115`, `src/lib/stripe.ts:10-14`, `prisma/schema.prisma:22`
- **Impact:** Two compounding problems: (1) the stored period-end is an Invalid Date for the configured API version, so any future expiry logic built on it is broken from the start; (2) because role is only downgraded to FREE on the terminal customer.subscription.deleted event, a subscription that goes past_due/unpaid (failed renewal) keeps the user on PREMIUM — ad-free and premium-gated content — through Stripe's entire dunning/retry window until it is finally canceled. Premium access is granted longer than paid for.
- **Evidence:** The webhook stores period end via `new Date((subscription as unknown as { current_period_end: number }).current_period_end * 1000)` (lines 76, 94), reading current_period_end off the top-level Subscription. The Stripe client pins apiVersion '2025-09-30.clover' (stripe.ts:12) and stripe@19.3.1 is installed. In that SDK, current_period_end was REMOVED from the Subscription type and lives on subscription items: `rg current_period_end node_modules/stripe/types/Subscriptions.d.ts` returns nothing, while node_modules/stripe/types/SubscriptionItems.d.ts:53 has `current_period_end: number`. The `as unknown as` cast is exactly what hides this from the compiler — at runtime the top-level field is undefined, so `new Date(undefined * 1000)` = Invalid Date written to `stripeCurrentPeriodEnd DateTime?`. Separately, `rg stripeCurrentPeriodEnd src/` shows it is ONLY ever written, never read — no gate consults it. And the webhook switch handles only checkout.session.completed, invoice.payment_succeeded, and customer.subscription.deleted (lines 61/83/101); there is no case for invoice.payment_failed or customer.subscription.updated, and no cron reconciles roles (cron/prune-data only deletes analytics/webhook/MMR rows).
- **Verifier note:** Claim is accurate. Two minor refinements: (a) The Invalid-Date bug (problem 1) is currently LATENT — it causes no live harm because stripeCurrentPeriodEnd is never read; it only breaks any future expiry-enforcement logic built on the field. The actively-impactful defect is the missing failed-payment/updated handling (problem 2). (b) The over-grant of premium is time-bounded by Stripe's dunning/Smart-Retries window (typically up to ~2-3 weeks by default), not indefinite — it ends when Stripe finally cancels and fires customer.subscription.deleted. Note also that fixing the SDK field path alone would NOT fix the entitlement leak, since no gate reads the date; a proper fix needs both correct field reads (subscription.items.data[0].current_period_end) AND new handlers for customer.subscription.updated/invoice.payment_failed that downgrade on past_due/unpaid (or an expiry check that actually consults the stored date). Severity high is appropriate for an ad-revenue product whose business model is gating, anchored at the lower end of high given the leak is dunning-window-bounded.
- **Fix:** Read period end from `subscription.items.data[0].current_period_end` (matching the pinned API version) and remove the `as unknown as` cast so the type system catches the field move. Add handlers for customer.subscription.updated (sync role to subscription.status: active/trialing → PREMIUM, past_due/unpaid/canceled/incomplete_expired → FREE) and treat invoice.payment_failed appropriately. Either consult stripeCurrentPeriodEnd in the premium check or remove it as dead state.

### 7. Post-checkout success_url points to a route that does not exist — paying users land on a 404
**Severity:** HIGH _(verified: confirmed)_ · **Area:** Payments, Pricing & Ads (Stripe checkout / post-payment UX)

- **Files:** `src/app/api/stripe/checkout/route.ts:67`, `src/app/premium/page.tsx`, `src/app/not-found.tsx`, `src/lib/auth.ts:138-153`
- **Impact:** A user who just paid is sent to a 404 page with no confirmation, and premium features (ad removal, gated content) may still appear locked for several minutes. This looks like a failed/broken payment immediately after charging the card — high support-ticket and refund/chargeback risk on the most sensitive moment of the funnel.

NEXT_PUBLIC_APP_URL also defaults to http://localhost:3000 in .env/.env.example. - **Verifier note:** Claim is accurate. Two clarifications on impact, not on the existence of the bug: (a) The payment itself is NOT lost — the Stripe webhook still upgrades role to PREMIUM in the DB regardless of where the browser lands, and the customer is charged correctly. Net: a paying user is reliably dropped on a generic 404 immediately after being charged — high severity stands. Fix is small: add src/app/premium/success/page.tsx (a confirmation page that can also call session update() to force an immediate token refresh) and ensure NEXT_PUBLIC_APP_URL is set to the prod domain.
- **Fix:** Create src/app/premium/success/page.tsx that confirms the purchase, reads the session_id, and ideally forces a session/JWT refresh (or a short poll) so premium reflects immediately rather than after the 5-minute window. Ensure NEXT_PUBLIC_APP_URL is set to the production origin in prod.
